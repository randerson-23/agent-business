# Security notes

Within Ten is a static site generated by Python scripts and published through
GitHub Pages. There is no PHP, no database and no server-side code running on
the site, so PHP and CMS exploits do not apply here. What can go wrong is the
build, because it reads text from outside (village feeds, scraped pages, issue
forms) and runs unattended with GitHub tokens.

## What is in place

- **Feed text is untrusted.** Event URLs from feeds and scraped pages are kept
  only if they are plain `http(s)` links (`safe_http_url`), so a `javascript:`
  or `data:` link cannot reach a card, email, feed or calendar file. Templates
  autoescape everything else; the few `|safe` uses are build-made JSON-LD
  (every `<` is escaped to `<`, so feed text cannot close the script tag)
  and a build-made QR code.
- **Calendar files** escape their text and URLs (RFC 5545) before writing.
- **Archived emails** are shown in a sandboxed iframe (no scripts).
- **Community submissions** go through a parser that accepts only `http(s)`
  links, write YAML through `yaml.safe_dump`, and always become a pull request
  a person reviews. Issue text is passed to scripts through environment
  variables, never spliced into code.
- **The link checker** requests only public `http(s)` hosts (never localhost,
  private or link-local addresses).
- **Workflows** declare their token permissions (`tests.yml` is read-only);
  secrets are passed only to the steps that need them; nothing runs from forks
  with secrets (`pull_request`, not `pull_request_target`).
- **Dependabot** proposes weekly updates for GitHub Actions and Python
  packages.

## Known gaps (owner decisions)

- Actions are pinned to major-version tags, not commit SHAs. Pinning needs the
  SHAs looked up from each action's repository.
- `requirements.txt` uses minimum versions, so a build installs the newest
  release. A lock file would stop a bad release arriving unreviewed.
- No `Content-Security-Policy` is set (GitHub Pages cannot send headers; a
  `<meta>` policy would need testing against the inline scripts and fonts).

## Reporting

Email the contact address on the site's About page. Do not open a public issue
for a vulnerability.
